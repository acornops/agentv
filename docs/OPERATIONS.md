# Operations

The AgentV is outbound-only. It connects to
`ACORNOPS_AGENT_PLATFORM_URL/api/v1/agent/connect`, performs a
`lifecycle/handshake`, sends heartbeats, uploads bounded host snapshots, and
serves strict JSON-RPC tool calls. It remains read-only unless local, remote,
and helper policy all enable `restart_service`.

Linux/systemd installs use `packaging/systemd/acornops-agentv.service` and
`/etc/acornops/agentv.env`. Keep the env file owned by `root:acornops-agent`
with mode `0640`.

For the initial bootstrap, both host `curl` and the selected Node runtime must
already trust the control-plane certificate. Install a private root in the host trust
store before onboarding. After installation, a root-managed PEM path in
`ACORNOPS_AGENT_ADDITIONAL_CA_BUNDLE_FILE` adds runtime trust without replacing
public roots or disabling certificate and hostname verification. Repair,
upgrade, and credential replacement preserve this setting.

## Runtime Requirements

- Node.js 22 or newer at `/usr/bin/node` or `/usr/local/bin/node`, or a container
  image built from this repository. The executable, its ancestors, and every
  symlink traversal must be root-owned and not group/world writable, and the
  runtime must be readable/executable by the service user. Per-user/home-directory
  runtimes are not supported.
- Linux with systemd for `ACORNOPS_VM_COLLECTOR_MODE=live`.
- curl with HTTPS support and a current trusted CA store for release downloads.
  Bootstrap downloads are tested with curl 7.68 and the qualified host's curl.
  They use `--retry 3` for curl's standard transient failures, not the newer
  `--retry-all-errors` option. HTTPS-only redirects, certificate validation,
  download timeouts, and archive checksum verification remain required; the
  installer does not install or upgrade curl.
- Network egress from the VM to the AcornOps control-plane WebSocket endpoint.
- A one-use enrollment command for initial installation, or an existing
  root-owned AgentV environment for repair and upgrade.
- HTTPS transport to the control plane. Plaintext `http://` requires the
  explicit local-development override and must not be used in production.

## Systemd Model

On first installation the installer checks `/usr/bin/node` followed by
`/usr/local/bin/node` and chooses the first trusted, supported runtime. This
supports a system-wide `sudo n` installation alongside an older OS Node. It does
not search the caller's `PATH`. The canonical absolute path is saved as data in
`/opt/acornops/agentv/node-path` (`root:root`, `0644`). Repair and upgrades retain
that selection. Existing installations without this file keep their original
`/usr/bin/node` meaning until installation selects and records a runtime.

The agent, root helper, and doctor use
`/usr/local/libexec/acornops-agentv-node`, which validates the stored path and
execs Node. `NODE_OPTIONS` and `NODE_PATH` are not inherited by installer Node
commands or the launcher. A missing, unsupported, or unsafe pinned runtime fails
explicitly; starting a service does not discover a replacement. Restore a
supported, trusted Node at the recorded path before retrying. Do not replace the
OS's `/usr/bin/node` merely to satisfy AgentV.

The main service runs as `acornops-agent` with readiness/watchdog notification,
`NoNewPrivileges`, private devices, kernel protections, restricted namespaces,
and explicit address families. The separate helper runs as root with no network
access and may write only its bounded action ledger.

Systemd starts Node as the tracked main process. Node invokes the fixed
`/usr/bin/systemd-notify` binary for bounded readiness and watchdog messages;
`NotifyAccess=all` permits those short-lived notifier children from this
service cgroup. Releases need no target-side compiler or native addon build.

Operational files:

- Unit: `packaging/systemd/acornops-agentv.service`
- Helper: `packaging/systemd/acornops-agentv-actions.socket` and `.service`
- Environment template: `packaging/systemd/agentv.env.example`
- Install helper: `packaging/systemd/install.sh`
- Secret-free transaction worker: `packaging/systemd/install-worker.sh`
- Boot recovery helper/unit: `packaging/systemd/acornops-agentv-install-recover`
  and `acornops-agentv-install-recovery.service`
- Uninstall helper: `packaging/systemd/uninstall.sh`

For normal onboarding, run only the exact version-pinned command generated by
the AcornOps management console. Initial and credential-replacement commands
carry a target-bound enrollment token that is single-use and expires after 15
minutes; the durable AgentV key is returned only to the root installer. The
copied command may remain in shell history, but its enrollment token is useless
after a successful exchange; clear the entry when host policy requires it.
Repair and upgrade commands reuse the matching root-owned environment. The
bootstrap verifies the archive checksum, records rollback state, and restores
the prior release, runtime selection, and configuration when cutover fails. The
token-bearing bootstrap process is replaced by a worker whose arguments contain no
credentials. A successful normal handshake writes
`/run/acornops-agentv/authenticated`, which
the installer uses together with the protected control-plane transaction to
confirm cutover or rollback connectivity.

Credential replacement first authenticates provisionally. That connection has
no tools and cannot claim the target. Commit promotes the candidate credential,
keeps the prior credential in a 30-minute rollback grace period, then requires
the normally authenticated AgentV connection to become ready. Durable
credentials do not expire or rotate on a schedule.

Incomplete transaction state is root-only under
`/var/lib/acornops-agentv/install-transactions`. At boot, recovery queries the
protected transaction status. It retains a committed candidate, cancels and
restores an uncommitted candidate, and retries without changing credentials if
the control plane cannot be reached. Commit and rollback authorization expires
after one hour; the same protected secret can only read final status afterward,
which lets a host recover after a longer outage without reopening mutation. If
the 30-minute credential rollback grace has closed, recovery restores the
already-committed candidate because it is the only credential the control plane
still accepts.

The transaction also retains the candidate runtime path so recovery can query
remote status after a failed first installation removes the local selection.
Legacy transactions without runtime snapshots continue to mean `/usr/bin/node`.
Uninstall removes the launcher with the units but preserves the selected-path
file with the rest of the installation data for a subsequent reinstall.

If an installer reports that an incomplete transaction exists, run
`sudo systemctl start acornops-agentv-install-recovery.service` and inspect that
unit's journal. Do not delete the root-owned transaction directory while
recovery is pending.

The tag release workflow runs the complete systemd gate on a fresh
GitHub-hosted Ubuntu 24.04 VM before publishing. It exercises bootstrap,
authentication, same-version rerun, credential replacement, upgrade, rollback,
boot recovery, and uninstall preservation. Ubuntu 24.04 LTS is the only
qualified first-release host; other distributions require equivalent live
evidence before they can be documented as supported.

The installer adds `acornops-agent` to `systemd-journal` when that group exists.
Run `sudo acornops-agentv-doctor` to verify configuration, binaries, journal
access, filesystem collection, TLS, and optional helper policy. The wrapper
drops privileges before checking host access, so its result reflects the actual
`acornops-agent` service identity rather than root's permissions.

## Optional service restart

Writes are disabled by default. For production onboarding, select read-write
access in the management console and add each exact restartable `.service`
unit before generating the command. The enrollment-bound policy is returned
only to the root installer, which atomically writes
`/etc/acornops/agentv-actions.json`, sets
`ACORNOPS_AGENT_WRITE_ENABLED=true`, and enables
`acornops-agentv-actions.socket`. Repair preserves and validates the local
policy; token-backed replacement re-applies the enrollment snapshot. Both
restore the prior policy on failure. Globs, aliases, AgentV's own units,
arbitrary commands, sudo, and unrestricted `systemctl` are rejected. Editing
these files manually is not a supported way to change the control-plane policy.

For the Docker-only mock fixture, set both `ACORNOPS_AGENT_WRITE_ENABLED=true`
and `ACORNOPS_AGENT_MOCK_ACTIONS_ENABLED=true` to simulate a restart of its
single fixture service, `ssh.service`. This path never contacts systemd or a
host helper and is rejected outside mock collector mode.

### Restart precondition failures

Before requesting a restart, call `get_service` for the exact unit and copy
`restart_preconditions.active_state`, `sub_state`, and (when present)
`invocation_id` into the matching `expected_*` arguments. Prefer separate
machine tokens such as `active` and `running`; the invocation ID identifies the
observed service instance, not the tool call or a retry attempt.

The tool also accepts the exact display form `state (substate)`, such as
`active (running)`, only when the embedded substate agrees with
`expected_sub_state`. It converts the active-state representation before the
action client, preserving the caller's arguments and every other expectation.
Malformed or contradictory states return `INVALID_ARGUMENTS` before helper
access. This does not fetch replacement expectations or relax the helper's
exact live-state and invocation-ID checks.

`PRECONDITION_FAILED` with `outcome: not_started` means the helper refused the
request before restarting. State/instance mismatch errors identify the first
mismatched field. Compare the supplied arguments with the preceding read: the
state may have changed, or the arguments may not match that read.
Read the service again before proposing a new restart; retain approval and
allowlist checks. Do not drop an observed invocation ID to bypass the guard.
An `unknown` outcome is different: inspect the service before deciding what to
do, and do not blindly retry a possibly completed restart.

AgentV `v0.0.1-experimental.13` added read-before-restart guidance but did not
normalize display-form inputs. The correction is included in
`v0.0.1-experimental.14`. Generate **Upgrade or repair AgentV** from VM Settings once that
release is selected by the platform, and run the command on the VM. A platform
redeployment does not upgrade installed agents. Confirm the connected version
after it reconnects, then start a new run with a fresh service read rather than
retrying old arguments or approvals.

## Logs And Diagnostics

Use journalctl for systemd installs:

```bash
journalctl -u acornops-agentv -f
```

The agent logs startup configuration without secrets, WebSocket connection status, handshake acknowledgement, snapshot upload summaries, snapshot collection failures, and WebSocket errors.

## Filesystem Capacity Findings

AgentV emits `FILESYSTEM_PRESSURE` at 90% used capacity, except for the known
immutable image formats `squashfs`, `erofs`, `cramfs`, `romfs`, and `iso9660`.
These images can report 100% usage by design, including Snap packages mounted
under `/snap`. Their filesystem facts remain available through `list_filesystems`
and snapshots, subject to the existing collection and snapshot limits.

Snapshot capacity findings are derived from the complete filesystem result
within the adapter's existing 5-second, 1 MiB-per-command `df` bounds, before
retaining at most 50 raw filesystem inventory rows in mount order. Thus a
finding can name a filesystem absent from `filesystems`; the snapshot's
`truncation.filesystems` counts raw rows omitted by both the inventory limit and
later byte-budget trimming. `finding_coverage.filesystems: complete` separately
confirms that all collected mounts were evaluated, allowing the control plane to
recover an old issue even when its mount is outside the retained inventory.
The independent `finding_coverage.services` follows the same rule before byte
trimming, but remains `incomplete` when the failed-service collector omits rows
beyond its 50-service limit. Failed or incomplete collection reports `incomplete`.
The public `list_filesystems` tool still applies
its requested limit normally. Findings are not trimmed to fit: if required
sections exceed the snapshot byte budget after optional facts are removed, the
whole snapshot is dropped. A failed filesystem command is reported through
`collector_health`, not as a healthy empty collection.

Exclusions use filesystem type, not mount paths, loop-device names, or
`read_only`. The latter describes AgentV's mount namespace: `ProtectSystem=strict`
can make ordinary host disks appear read-only to the agent. Other types,
including unknown types, network filesystems, tmpfs, and writable overlays,
remain eligible for capacity findings. Memory and service findings are unchanged.

Existing hosts must upgrade AgentV to a release containing this behavior; a
console or control-plane redeploy alone does not change agent-generated findings.
After new snapshots stop reporting an image-capacity finding, its existing issue
recovers and resolves through normal control-plane reconciliation. The matching
control-plane fix derives inventory pressure badges from these findings, too.
Do not delete Snap packages or issue records just to clear these false positives.

## Failure Modes

- Control plane unavailable: the agent reconnects with capped equal-jitter exponential backoff.
- Host adapter unavailable: collector health reports degraded/unavailable rather than a successful empty result.
- Oversized snapshot: optional entries are deterministically trimmed, then the snapshot is dropped if compressed bytes still exceed the negotiated hard limit.
- Ambiguous restart: the helper/executor reports `outcome: unknown`; the action is never marked retryable.
- Invalid configuration: startup fails fast with a clear environment-variable error.

## Rollback

Systemd installs can roll back atomically by replacing
`/opt/acornops/agentv/current` with a symlink to a preserved release and then
restarting the main service. Stop any currently active socket helper so the next
socket activation starts it from the selected release:

```bash
ln -s /opt/acornops/agentv/releases/<version> /opt/acornops/agentv/.rollback
mv -Tf /opt/acornops/agentv/.rollback /opt/acornops/agentv/current
systemctl restart acornops-agentv.service
systemctl stop acornops-agentv-actions.service
```

The action socket remains enabled and starts the selected helper on the next
request. Configuration, action policy, ledger, and prior releases are preserved
by both upgrade and uninstall.

## Windows read runtime boundary

Windows uses an explicit Windows/SCM configuration; Linux/systemd remains the
default. Windows writes are disabled locally regardless of remote policy.
Read-only native collection is currently limited to Windows Server 2022/2025
x64 and Node 22/24. Synthetic mock data is development-only and does not qualify
host permissions or service installation. See the
[Windows read runtime contract](contracts/windows-read-runtime.md).

`dist/windows-service-entry.js --config <absolute protected JSON path>` is a
private child entrypoint for the separately reviewed native SCM host. It waits
for strict newline JSON START before importing runtime/config modules. START
contains `trustedSystemDirectory` and a strict `launch` object with UUID
`launchId`, hexadecimal SHA-256 `configSha256`, and absolute `stateDirectory`. The host supplies the trusted directory
from OS APIs only after assigning the child to its Job Object. It sends
`{"command":"STOP"}` for shutdown. STOP during asynchronous startup is retained;
EOF after START requests shutdown. START has a 10-second deadline, runtime
startup/shutdown each have a 15-second deadline, lines are capped at 4096 bytes
and total control input at 8192 bytes. Runtime shutdown is idempotent.

The config is at most 64 KiB and has the strict shape
`{"version":1,"settings":{"ACORNOPS_AGENT_PLATFORM_URL":"https://...","ACORNOPS_TARGET_ID":"...","ACORNOPS_AGENT_KEY":"..."}}`.
Only named AgentV settings are projected. The service entry enforces
Windows/SCM/live/read-only settings; conflicting values, arbitrary keys and
non-string values fail. Node/runtime/system-directory paths are outside config.
The repository Framework 4.8 host is being qualified separately. It derives
ProgramData from OS folder APIs, fixes config at `AcornOps\AgentV\config.json`,
and grants the service SID access only to the protected runtime/config and its
own log/state directories. Before START it clears old authentication evidence,
hashes config, assigns Node to a kill-on-close Job Object, and sends a fresh
launch identity. The child checks that config hash before importing the runtime.
On authenticated connection it atomically publishes bounded `authenticated.json`
evidence; disconnect removes it. This file grants no recovery authority.

The native host has no enrollment HTTP or installer logic. SCM crash recovery
uses 10/30/60-second restart delays and a one-day reset. Orderly stop waits up to
15 seconds, terminates remaining job members, and observes zero active processes
within a further 5 seconds. Child stdout/stderr use 5 MiB current files and three
retained rotations each. Sink failure drains/discards data. Hosted native results,
transactional installation and reboot qualification remain required before any
Windows onboarding activation.
